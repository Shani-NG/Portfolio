3\. Executive Summary

HOWTOOL was a SaaS knowledge-management platform designed for organizations operating complex capital equipment. Knowledge managers and administrators created interactive guides in a web-based KMS, while field technicians accessed those guides through a mobile application for training, troubleshooting, and operational support.

The product addressed a clear need: expert knowledge had to become usable guidance at the moment of action. The main UX challenge, however, was inside the authoring system itself. Navigation was complex, the content-creation process required a steep learning curve, the editor did not reliably reflect the final mobile result, and creators often discovered missing information or structural problems only after publication.

The redesign rebuilt the KMS foundations around clearer navigation, role-based access, structured creation, preview, automated validation, contextual help, and a more reliable path from expert logic to field action.

4\. Project Context

System type  
A SaaS Knowledge Management System with a web-based authoring environment and a mobile application for field use.

Business and operational context  
Organizations operating complex equipment needed a way to capture expert knowledge, organize it, publish it, and deliver it as interactive step-by-step guidance to technicians.

Product vision  
Move beyond static manuals and PDFs toward reusable, contextual operational guidance.

Core product tension  
The product promised to simplify complex knowledge for field users, but the creation and publishing workflow was itself too complex and unreliable.

7\. Problem Definition

7.1 Navigation and orientation  
Users frequently lost context while moving through complex projects, pages, permissions, and content structures.

7.2 High creation complexity  
Creating a guide required a steep learning curve and placed too much cognitive burden on content creators.

7.3 Editor-to-output inconsistency  
The web editor did not reliably predict the structure, segmentation, or layout of the final mobile guide.

7.4 Late error discovery  
Missing fields, invalid structures, and content problems often appeared only after publication.

7.5 Repeated publishing cycles  
Creators had to publish, inspect, correct, and republish until the mobile output matched their intent.

7.6 Insufficient in-product guidance  
Users lacked clear support for unfamiliar controls, empty states, required information, and complex publishing tasks.

7.7 Knowledge scalability  
If expert knowledge was difficult to structure, validate, and publish, the organization could not reliably scale it into field guidance.

9\. Strategic Product Reframing

The project was not only a visual redesign. It restructured how expert knowledge moved through the product.

The product flow became  
Create → Organize → Preview → Validate → Publish → Use in the field

Strategic principles  
\- Knowledge creation should be structured but not unnecessarily technical.  
\- Creators should understand the likely field result before publication.  
\- Critical publishing errors should be prevented, not discovered later.  
\- Guidance should appear inside the workflow at the moment it is needed.  
\- Different roles should receive relevant access, tools, and information.  
\- The authoring experience should reflect the same clarity promised to field users.

10\. Documented Solution Areas

10.1 Rebuilt Information Architecture  
The team reviewed current and planned features, grouped them by user need, clarified permissions, removed redundant elements, and defined an MVP roadmap.

Documented value  
Created a clearer system structure and reduced access friction around key capabilities.

10.2 Clearer Navigation and Orientation  
The redesigned KMS introduced:  
\- Refined vertical navigation.  
\- A two-column page structure.  
\- Contextual tabs.  
\- Clearer content areas.  
\- Role-based dashboards.

Documented value  
Users could move through complex projects without losing context as easily.

10.3 Role-Based Dashboards  
Dashboards and access patterns were tailored to different user roles and responsibilities.

Documented value  
Relevant tools and information could be surfaced more directly for administrators, managers, and other system roles.

10.4 Preview Before Publication  
Creators could preview full projects or individual items without publishing them.

Documented value  
The expected mobile result could be reviewed before reaching field users, helping identify layout, segmentation, and text problems earlier.

10.5 Server–Client Synchronization  
Technical changes supported better synchronization between the KMS server and the mobile client.

Documented value  
Reduced the gap between authored content and the delivered mobile experience.

Ownership guardrail  
Describe this as cross-functional product and UX work. Do not claim sole engineering implementation ownership.

10.6 Automated Publishing Validation  
The team mapped common publishing mistakes and created an automated audit and validation mechanism.

Documented behavior  
\- Checked for missing or invalid information.  
\- Identified structural issues before release.  
\- Blocked publication when critical problems remained unresolved.

Documented value  
Reduced repeated publishing cycles and improved confidence in the published result.

10.7 Contextual Help  
The redesign added:  
\- Tooltips for unfamiliar controls.  
\- Empty states with explanations and next steps.  
\- Supportive illustrations.  
\- In-workflow guidance.

Documented value  
Helped users understand what the system expected without requiring separate documentation.

10.8 Guided Creation and Publishing Flows  
Wizards guided users through multi-step actions from editing through publication.

Documented value  
Reduced ambiguity in complex creation and publishing tasks.

10.9 Mobile Operational Guidance  
The wider HOWTOOL product delivered interactive step-by-step guides through a mobile application for training and troubleshooting.

Documented value  
Expert knowledge became available closer to the point of need.

Evidence boundary  
The supplied sources support the platform purpose and mobile-delivery model. Strong claims about exact downtime, error, or training reductions are not currently verified.

11\. Pre-AI Relevance

Documented interpretation  
HOWTOOL addressed a product question that remains relevant in AI systems: how to transform complex expert knowledge into contextual assistance.

What the system did  
It structured expert-authored content, rules, and workflow logic so that knowledge could be reused as guided action.

What the system did not do  
\- It did not use generative AI.  
\- It did not independently generate expert knowledge.  
\- It should not be described as an LLM, RAG, agent, or prompt-engineering system.

Safe comparison  
HOWTOOL can be described as a pre-generative-AI example of structured knowledge automation and contextual guidance.

Unsafe comparison  
Do not claim that it invented prompt engineering, generative knowledge creation, or modern AI assistance.
